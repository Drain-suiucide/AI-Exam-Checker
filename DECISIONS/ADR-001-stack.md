# ADR-001: Технологический стек

- Статус: **Proposed** (требует утверждения владельцем проекта)
- Дата: 2026-10-27
- Задача: T-003
- Связано: [ARCHITECTURE.md](../ARCHITECTURE.md), PROJECT_CONTEXT.md («стек предварительный до ADR»)

## Контекст

Систему поддерживает один разработчик с ИИ-агентами. MVP: один предмет, одно задание, один поток «скан → OCR → правка → оценка → объяснение → экспертная проверка». Нагрузка демонстрационная (единицы одновременных пользователей). Критичны: простота запуска (`docker compose up`), предсказуемость для агентов, воспроизводимость, минимум ПДн.

## Решение

| Технология | Решение | Обоснование и ограничения |
|---|---|---|
| React + TypeScript + Vite | **Принять** | Статическая SPA, SSR не нужен. TanStack Query для опроса статусов. Типы API генерируются из `openapi.json`. Без глобального стейт-менеджера и UI-кита сверх необходимого. `tsc --strict`, eslint |
| Python 3.12 + FastAPI | **Принять** | Pydantic-схемы дают валидацию и OpenAPI «бесплатно»; экосистема OCR/LLM на Python |
| SQLAlchemy 2.0, **синхронный**, psycopg 3 | **Принять** | Синхронный код проще для агентов и без ловушек ленивой загрузки async-ORM. Фоновые задачи идут в пуле потоков; для демо-нагрузки достаточно |
| PostgreSQL 16 | **Принять** | JSONB, частичные уникальные индексы и атомарные переходы состояний — основа идемпотентности и «одна оценка на версию текста». SQLite отвергнут: нет частичной конкурентности и паритета с продом |
| Alembic | **Принять** | Автогенерация только как черновик; `downgrade` обязателен; перечисления — `text` + `CHECK` |
| Pydantic v2 + pydantic-settings | **Принять** | Схемы API, схема ответа LLM, конфигурация из окружения. Отдельный слой SQLModel не берём: смешивает DB- и API-модели |
| Docker Compose | **Принять** | Сервисы: `db`, `backend`, `web` (nginx: статика SPA + прокси `/api`, один origin — без CORS). В разработке — `vite dev` с прокси |
| pytest | **Принять** | Тесты против PostgreSQL из compose; OCR и LLM — `mock`-адаптеры; без внешних сетей. Frontend — Vitest |
| Файловое хранилище | **Локальный том за интерфейсом** | См. ADR-002 |
| Отдельный OCR | **Модуль в процессе** (`OcrEngine`) | Не сервис. Движок выбирается в T-008 по бенчмарку, адаптеры сменяемы |
| Движок критериев и оценивания | **Модуль в процессе** (`EvaluationEngine`) | Чистая логика поверх `LlmClient`; ADR-003 |
| Менеджеры пакетов и качество | **uv** (Python), **npm** (frontend), ruff, mypy, eslint | Минимум инструментов; версии фиксируются lock-файлами |

Версии: Python ≥ 3.12; Node.js — актуальная LTS на момент каркаса (T-005); остальное фиксируется lock-файлами в T-005.

## Что сознательно не добавляем

| Технология | Почему нет | Условие пересмотра |
|---|---|---|
| Микросервисы | Один разработчик, один процесс; сетевые границы дороже интерфейсных | Независимое масштабирование OCR/LLM |
| Celery/Redis/RabbitMQ | Фоновые задачи редки и короткие; состояние в БД; восстановление при старте | Сотни параллельных проверок. Сначала — отдельный процесс на `FOR UPDATE SKIP LOCKED` |
| Kubernetes | Один `docker compose` достаточен | Многосерверный прод |
| Векторная БД/RAG | Критерии небольшие и целиком входят в промпт; поиск по корпусу не нужен | Расширение на много заданий с большими материалами |
| MinIO/S3 | См. ADR-002 | Несколько экземпляров backend |
| WebSocket/SSE | Опрос раз в 2 с проще и надёжнее | Нужна мгновенная доставка |
| Внешняя аутентификация | Аккаунты вне MVP | Личные кабинеты |
| GraphQL, Next.js/SSR | Нет потребности | — |

## Последствия

- Один процесс backend: падение прерывает фоновую работу; это отражено статусом `INTERRUPTED` и восстановлением при старте.
- Горизонтальное масштабирование backend потребует вынести фон и хранилище (описанный путь роста).
- Внешний LLM-провайдер — единственная сетевая зависимость; ограничение приватности фиксируется в SECURITY.md.
- Сторонние библиотеки и версии выбирает T-005; смена любой позиции таблицы выше — новый ADR.
