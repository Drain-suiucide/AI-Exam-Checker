# ADR-002: Хранение загруженных файлов

- Статус: **Proposed**
- Дата: 2026-10-27
- Задача: T-003
- Связано: [ARCHITECTURE.md](../ARCHITECTURE.md), [DATA_MODEL.md](../DATA_MODEL.md) (`uploaded_files`), SECURITY.md

## Контекст

Пользователь загружает до 4 изображений скана (≤ 8 MiB каждое). Данные только синтетические или обезличенные, но изображения рукописного текста могут содержать метаданные (EXIF, GPS). Нужны: простой запуск, контроль доступа, автоудаление, возможность позже перейти на объектное хранилище.

## Решение

1. **Локальная файловая система в Docker named volume** (`uploads`) за интерфейсом `StorageBackend` (`put/open/exists/delete/delete_prefix`, см. ARCHITECTURE.md п. 6.1). Реализация MVP — `LocalFileStorage`.
2. **Ключ объекта:** `submissions/{submission_id}/{file_id}.{ext}`. Имена исходных файлов не сохраняются.
3. **Метаданные** (тип, размер, размеры в пикселях, SHA-256, порядок страниц) — в таблице `uploaded_files`; сами байты — только в хранилище, не в БД.
4. **Приём файла:**
   - тип определяется по содержимому (сигнатура + декодирование Pillow), не по заголовку клиента;
   - допустимы JPEG, PNG, WebP; PDF и HEIC не принимаются в MVP;
   - лимиты: ≤ 8 MiB на файл, ≤ 4 файлов, ≤ 40 Мпикс (защита от «бомб декомпрессии»);
   - **нормализация перед сохранением:** снять EXIF и прочие метаданные, применить ориентацию, ограничить длинную сторону 4096 px, пересохранить в том же семействе формата. Хранится только нормализованная копия, оригинал не сохраняется;
   - запись атомарная (временный файл + `rename`); при ошибке на любом шаге уже записанные файлы удаляются.
5. **Выдача:** только через `GET /submissions/{id}/files/{file_id}/content` с проверкой доступа; `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`. Каталог не публикуется веб-сервером.
6. **Жизненный цикл:** удаление отправки (по запросу или по `expires_at`) вызывает `delete_prefix("submissions/{id}/")`. Фоновая очистка раз в час и команда `purge-expired`.
7. **Потолок:** `MAX_STORAGE_BYTES` (по умолчанию 2 GiB); при превышении новые загрузки отклоняются `429 RATE_LIMITED`.
8. **Доступ к тому:** только контейнер backend, непривилегированный пользователь, права `0700`. Резервное копирование не делается (демо-данные эфемерны).

## Рассмотренные альтернативы

| Вариант | Причина отказа |
|---|---|
| Хранить байты в PostgreSQL (`bytea`) | Раздувает БД и бэкапы, усложняет потоковую выдачу; выигрыш — единая транзакция — для MVP не нужен |
| MinIO/S3 сразу | Отдельный сервис, ключи, политики — избыточно для одного экземпляра |
| Сохранять оригиналы без нормализации | Утечка EXIF, риск «бомб», разные ориентации ломают OCR |
| Публичные ссылки/presigned URL | Нет аккаунтов; прямой доступ обходит проверку токена |
| Антивирусная проверка (ClamAV) | Файлы перекодируются Pillow и не исполняются; не добавляем в MVP. Пересмотреть при приёме PDF |

## Последствия

- Привязка к одному экземпляру backend (том локален). Для нескольких экземпляров — реализовать `S3Storage` (S3-совместимый API) без изменений сервисов; ключи уже совместимы.
- Нормализация необратима: повторное распознавание идёт по нормализованным изображениям. Это допустимо и повышает воспроизводимость.
- Pillow — поверхность атаки: версии обновляются, ограничения по пикселям обязательны (`Image.MAX_IMAGE_PIXELS`).
- Потеря тома = потеря файлов, но не результатов (результаты — в БД); при удалении файлов отправка остаётся только до TTL.

## Критерии пересмотра

Более одного экземпляра backend; требование долговременного хранения; приём PDF; объём тома близок к потолку.
