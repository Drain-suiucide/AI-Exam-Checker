# ADR-003: Версионирование оценивания

- Статус: **Proposed**
- Дата: 2026-10-27
- Задача: T-003
- Связано: [DATA_MODEL.md](../DATA_MODEL.md), [API_CONTRACT.md](../API_CONTRACT.md), [ARCHITECTURE.md](../ARCHITECTURE.md)

## Контекст

Критерии ФИПИ, текст задания, промпт и модель со временем меняются. Требование: каждая проверка связана с конкретными версиями экзамена, задания, критериев, промпта/конфигурации и модели, а исторические результаты **не пересчитываются незаметно**. Модель недетерминирована, поэтому повторный вызов с теми же входными данными даёт другой результат.

## Решение

### 1. Неизменяемые версионируемые сущности

Версионируются: `exam_versions`, `task_versions`, `criteria_versions` (с дочерними `criteria`), `evaluation_profiles` (промпты + модель + параметры). Жизненный цикл: `draft → approved → retired`. После `approved` строки **не изменяются**, даже ради опечатки: любая правка создаёт новую версию (`version + 1`).

Каждая версия имеет `content_sha256` — хэш канонического JSON её содержимого (ключи отсортированы, UTF-8, NFC, без пробелов; для критериев — вместе с дочерними строками). Seed-загрузчик отказывается изменять утверждённую версию, если хэш не совпал (`python -m app.cli seed` завершается ошибкой).

### 2. Закреплённая конфигурация

`exam_configurations` связывает ровно одну версию экзамена, задания, критериев и профиль оценивания. Утвердить конфигурацию можно, только если все компоненты утверждены. Отправка закрепляет `exam_configuration_id` при создании и никогда его не меняет. Проверить по новой конфигурации — создать новую отправку.

### 3. Снимок в результате оценки

Строка `evaluations` дополнительно копирует `task_version_id`, `criteria_version_id`, `evaluation_profile_id`, `prompt_sha256`, `model_provider`, `model_requested`, фактическую `model_reported` (снимок модели из ответа провайдера), `input_sha256` (хэш реально отправленного промпта), `transcription_id` и `transcription_sha256`. Оценка остаётся объяснимой, даже если конфигурация позже будет выведена из обращения.

### 4. Результаты неизменяемы

- Строки `evaluations`, `criterion_scores`, `evidence_refs` после успешного завершения не обновляются.
- Правка текста создаёт новую версию транскрипции; прежняя оценка остаётся доступной с `is_current = false`.
- Повторная оценка — новая строка (`attempt_no`), которая не заменяет старую. Для одной версии текста допускается только одна оценка в `running`/`succeeded` (частичный уникальный индекс); неудачных попыток не более 3.
- Экспертное решение — отдельная запись; итог (`final`) собирается из оценки и решения, исходная оценка не меняется.
- Утверждение новой версии критериев не затрагивает ни одной существующей оценки.

### 5. Что считается изменением версии

| Изменение | Новая версия чего |
|---|---|
| Текст, материалы, максимальный балл задания | `task_versions` |
| Название, описание, уровни, максимум любого критерия; добавление/удаление критерия; правило агрегации | `criteria_versions` |
| Промпт, схема ответа, модель, температура, пороги, тайм-ауты | `evaluation_profiles` |
| Смена любой из версий выше в наборе | новая `exam_configurations` |
| Обновление редакции официального материала | новая строка `source_editions` и новые версии, которые на неё ссылаются |

### 6. Выбор версии по умолчанию

`GET /exam-configurations` отдаёт утверждённые конфигурации, `is_default` — первой. Одна утверждённая конфигурация по умолчанию (частичный уникальный индекс). Переключение по умолчанию на новую версию влияет только на новые отправки.

### 7. Воспроизводимость и её границы

Гарантируется: какие тексты, критерии, промпт и модель были использованы; что оценка не менялась после записи. **Не гарантируется** побитовая воспроизводимость ответа LLM: провайдеры не обязаны давать идентичный результат при `temperature = 0`. Поэтому сохраняются `raw_output` и `input_sha256`, а повторный запуск считается новой оценкой, а не «пересчётом». Уверенность модели — самооценка, не калиброванная вероятность; в интерфейсе так и подписывается.

### 8. Статус «неутверждено»

Пока T-001/T-002 не завершены, конфигурации остаются `draft`. Оценка по ним возможна лишь при `ALLOW_UNAPPROVED_CONFIG=true`; в результате `versions.exam_configuration_status = "draft"`, и интерфейс обязан показать предупреждение. Приёмочный критерий «используются подтверждённые задание и критерии» выполняется только на `approved`.

## Рассмотренные альтернативы

| Вариант | Причина отказа |
|---|---|
| Изменяемые записи + таблица истории | Легко потерять связь результата с версией; нужна дисциплина на каждом UPDATE |
| Хранить критерии только в git, в БД ссылка на коммит | Результат нельзя объяснить без доступа к репозиторию; сложнее выборки |
| Копировать весь снимок конфигурации в каждую оценку (JSON) | Дублирование; неизменяемые версии с хэшами решают ту же задачу компактнее |
| Автоматический пересчёт при выходе новых критериев | Прямо противоречит требованию «не пересчитывать незаметно» |
| SemVer для версий | Нужен только порядковый номер |

## Последствия

- Справочных таблиц больше, чем при изменяемой схеме, но их мало строк и они заполняются из seed-файлов.
- Исправление опечатки в критериях требует нового `criteria_version` и новой конфигурации; это сознательная цена.
- Отчётность «по версиям» строится соединением `evaluations` с версиями без вычислений.

## Критерии пересмотра

Появление нескольких заданий и редакторского интерфейса для критериев (потребуется управление версиями через API); необходимость повторной оценки старых ответов по новым критериям — тогда вводится явная операция «повторная проверка» с ссылкой на исходную оценку, а не изменение существующей.
