# Security

## Основные правила

Не использовать реальные персональные данные.

Не публиковать экзаменационные работы пользователей.

Использовать только синтетические данные в репозитории.

---

## Сообщение об уязвимостях

**Пожалуйста, не открывайте публичный issue для уязвимостей безопасности.**

Если вы обнаружили уязвимость:

1. **Куда сообщать:** используйте приватный канал GitHub — [Security Advisories](https://github.com/Drain-suiucide/AI-Exam-Checker/security/advisories/new) (раздел «Security» → «Report a vulnerability»). Если он недоступен, откройте issue **без технических деталей** с просьбой о приватном контакте.
2. **Что указать:** описание проблемы, затронутые компоненты, шаги воспроизведения, оценку влияния. Не включайте чужие персональные данные и реальные экзаменационные работы.
3. **Сроки реакции:** это исследовательский проект без SLA. Мы постараемся подтвердить получение в течение 7 дней и согласовать план исправления до публичного раскрытия.
4. **Ответственное раскрытие:** просим не публиковать детали уязвимости до выхода исправления или истечения 90 дней с момента подтверждения — в зависимости от того, что наступит раньше.

### Область применения (scope)

В scope: код репозитория (backend, frontend, docker-конфигурация), обработка файлов, промпт-инъекции в движке оценивания, утечки данных через API и логи.

Вне scope: уязвимости сторонних сервисов (Tesseract, LLM-провайдеры, Docker), социальная инженерия, DoS-атаки на демо-стенды, развёрнутые третьими лицами.

### Если секрет попал в историю Git

Простое удаление строки новым коммитом **не решает проблему**: секрет остаётся в истории. Необходимые действия:

1. Немедленно **ротировать секрет** (отозвать ключ/пароль у провайдера).
2. Сообщить об инциденте владельцу проекта.
3. Согласовать очистку истории (`git filter-repo` / BFG) с принудительным push — это ломает клоны участников, поэтому выполняется только по согласованию.

## Контроль доступа

Для MVP:

- без регистрации;
- без хранения персональных данных.
- Доступ осуществляется анонимно (на этапе исследовательского прототипа).

## Блокеры для публичного деплоя

Перед запуском публичного режима интегратор **обязан** закрыть следующие блокирующие риски или явно отказаться от запуска публичного режима:

1. **Аутентификация и авторизация (RBAC)**: Внедрить систему контроля доступа. Текущий анонимный доступ недопустим для работы с реальными экзаменационными работами и результатами.
2. **Rate Limiting (Защита от злоупотребления ресурсами)**: Ограничить частоту вызовов, особенно для ресурсоемких операций (OCR, LLM), для предотвращения отказа в обслуживании (DoS) и неконтролируемых расходов.
3. **Безопасность инфраструктуры**:
    - Настроить балансировщик нагрузки (Nginx) с жесткими лимитами на размер запроса (`client_max_body_size`) и таймаутами.
    - Провести аудит зависимостей (SAST) и сканирование Docker-образов на известные уязвимости.
    - Убедиться, что `DEBUG=False` и настроены строгие правила CORS.
4. **Правовые вопросы**: Утвердить политику обработки персональных данных и правила хранения/удаления файлов.

*Полный отчет по безопасности находится в `docs/security/security-review.md`.*
