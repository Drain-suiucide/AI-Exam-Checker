# Участие в разработке (Contributing)

Спасибо за интерес к AI Exam Checker! Это исследовательский прототип, и мы рады вкладу сообщества — от исправления опечаток до новых модулей.

## Как начать

1. Прочитайте [README.md](README.md) и [ARCHITECTURE.md](ARCHITECTURE.md) — они объясняют, что делает система и почему она устроена именно так.
2. Поднимите проект локально по [docs/deployment/local-development.md](docs/deployment/local-development.md).
3. Убедитесь, что тесты проходят: `cd backend && uv run pytest`, `cd frontend && npm test`.

## Правила, которые нельзя нарушать

Эти ограничения связаны с предметной областью (экзамены) и безопасностью:

1. **Никаких реальных данных учеников.** В код, тесты, фикстуры, документацию и git-историю не должны попадать реальные экзаменационные работы, персональные данные, фотографии бланков. Только синтетические данные.
2. **Никаких секретов.** Ключи API, пароли и токены — только через переменные окружения. `.env` игнорируется Git. Если секрет случайно попал в коммит — это инцидент: сообщите по процедуре из [SECURITY.md](SECURITY.md), секрет нужно ротировать, а историю — очищать.
3. **Контракты первичны.** Имена полей API и модели данных определены в [API_CONTRACT.md](API_CONTRACT.md) и [DATA_MODEL.md](DATA_MODEL.md). Их изменение требует отдельного обсуждения в issue до написания кода.
4. **Не заявляйте официальность.** Нельзя утверждать, что результаты системы совпадают с решениями экзаменационной комиссии, или что проект одобрен ФИПИ/Рособрнадзором. Критерии не «придумываются» моделью — они версионируются и трассируются к источникам.

## Процесс внесения изменений

1. **Issue сначала.** Для новой функциональности или изменения контрактов откройте issue и опишите задачу. Для мелких исправлений (опечатки, очевидные баги) можно сразу PR.
2. **Ветка от `main`.** Название: `feature/краткое-описание` или `fix/краткое-описание`.
3. **Тесты рядом с изменением.** Каждое изменение кода сопровождается тестами своего модуля. Все существующие тесты должны проходить.
4. **Линтеры.** Backend: `uv run ruff check app`. Frontend: `npm run lint` и `npm run build` (включает `tsc --strict`).
5. **Pull Request.** Опишите, что и зачем изменилось, сошлитесь на issue. PR требует прохождения тестов и review.

## Стандарты кода

- **Python 3.12+**: типизация обязательна (mypy strict), стиль — ruff (см. `backend/pyproject.toml`).
- **TypeScript**: `tsc --strict`, ESLint 9.
- **Комментарии и пользовательский интерфейс** — на русском языке.
- **Зависимости** фиксируются в lock-файлах (`uv.lock`, `package-lock.json`); они коммитятся.

## Структура владения

Исторически проект разделён на зоны ответственности (см. [ARCHITECTURE.md](ARCHITECTURE.md), п. 5): backend, frontend, OCR, evaluation, документация. При PR в чужую зону будьте готовы к более детальному review.

## Сообщение об уязвимостях

**Не открывайте публичный issue для уязвимостей.** Следуйте процедуре в [SECURITY.md](SECURITY.md).

## Лицензия

Лицензия проекта находится на согласовании у владельца. До появления файла LICENSE в корне репозитория код не считается лицензированным для переиспользования; отправляя PR, вы соглашаетесь, что ваш вклад будет распространяться под лицензией, которую выберет владелец проекта (планируется OSI-совместимая permissive-лицензия, предварительно MIT — она уже указана в метаданных `backend/pyproject.toml`).
