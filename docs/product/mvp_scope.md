AI Exam Checker — границы MVP, backlog и распределение ИИ-агентов
Статус: план реализации; программирование не выполнялось этим документом.
Версия: 0.1, 2026-10-26.
Цель: превратить ТЗ в управляемые задачи с одним владельцем, ограниченным набором файлов, явными зависимостями и проверяемой приёмкой.
1. Что именно строим
MVP — публичный конкурсный веб-прототип исследовательской проверки одного типа развёрнутого ответа по истории. Исследовательский кандидат — задание 19 ЕГЭ-2026: смысл исторического понятия и один конкретный исторический факт по истории России. Рассмотренная версия руководства ФИПИ описывает шкалу 0–2, но точное условие из КИМ и соответствие документов одной версии ещё нужно подтвердить. До этого live-оценивание реальной работы не считается методически готовым; можно демонстрировать только утверждённые предметным экспертом синтетические фикстуры.
В MVP включено
- одна версия подтверждённого задания и критериев;
- публичный demo-flow без аккаунтов;
- синтетические заранее размеченные примеры;
- ручной ввод и загрузка изображения;
- OCR с обязательной ручной проверкой распознанного текста;
- предлагаемая оценка 0–2 с объяснением и доказательными фрагментами;
- флаг неоднозначности/экспертной проверки и экспорт пакета на явное действие пользователя;
- ограниченная история текущей сессии и аудит ключевых событий без содержимого ответа в технических логах;
- документированные тесты, метрики и ограничения; Docker-based deployment после принятия ADR.
Вне MVP
- любой другой предмет, ОГЭ, другие годы без отдельной проверки критериев;
- официальное выставление государственного балла и обещание совпадения с решением экспертной комиссии;
- все задания/полный вариант ЕГЭ, мультимодальные задания с анализом изображений как исторического источника;
- регистрация, личные кабинеты, роли организаций, массовая обработка реальных работ;
- полноценная очередь и realtime-модерация человека, пока нет утверждённой аутентификации и операционного процесса;
- государственные интеграции, платежи, автодообучение, собственная большая языковая модель;
- автоматическое исправление текста без подтверждения и отдельные штрафы за грамотность/стиль/длину;
- постоянное хранение оригинальных изображений и необезличенных пользовательских ответов.
2. Решения и правила координации агентов
1. Один исполнитель — один владелец задачи. Дополнительный агент может делать review, но не должен менять файлы за владельца без передачи задачи.
2. Изолированные рабочие ветки/рабочие каталоги. Ветки сливаются через PR. Владелец задачи обязан не менять файлы за пределами списка Разрешённые файлы.
3. Контракты раньше реализации. API, схема данных, названия статусов и события аудита фиксируются в IMP-002 до параллельной разработки фронтенда/бекенда.
4. Исследовательские критерии — не промпт по умолчанию. IMP-001 должен закрыть предметные блокеры и подготовить утверждённый профиль. Нельзя поручать модели самостоятельно «придумать» официальные критерии.
5. Численные пороги выбираются после измерений. Для OCR, оценивания и latency сначала фиксируются набор/окружение/метод; метрики измеряются, затем владелец продукта и QA согласуют критерии допуска.
6. Реальные персональные данные запрещены. Используются синтетические либо документированно обезличенные/разрешённые данные. Запрещено коммитить реальные работы, ключи и секреты.
7. Тесты рядом с изменением. Каждая кодовая задача поставляет тесты своего модуля и описывает ручную проверку. Полный релиз блокируется до сквозного теста и security review.
8. Существующие крупные этапы T-001—T-014 сохраняются как верхний уровень. Задачи IMP-* уточняют их; после принятия данного плана интегратор может отдельно синхронизировать TASK_BOARD.md.
3. Параллельная работа и порядок этапов
Этап 0 — исследовательские и контрактные блокеры
Можно вести параллельно:
- IMP-001 — сверка официальных документов и экспертных трактовок;
- IMP-002 — архитектура, API и модель данных;
- IMP-003 — UX-flow и прототип без привязки к реальному API;
- IMP-014 — проект тестового набора и протокол измерений; размеченные случаи станут обязательными после утверждения IMP-001.
Этап 1 — каркас и общие контракты
Начать после принятия основных решений IMP-002:
- IMP-004 — каркас проекта/CI;
- IMP-005 — модель профиля критериев/версии;
- IMP-017 — первичный план контейнеров и деплоя может готовиться параллельно, но не фиксировать стек до ADR.
- IMP-013 — security/privacy review потоков данных, как только схема данных и внешние сервисы описаны.
Этап 2 — функциональные модули
После API/data contract и каркаса: IMP-006 (загрузка), IMP-007 (OCR), IMP-008 (ручной ввод/редактирование), IMP-009 (оценивание), IMP-010 (evidence), IMP-011 (экспорт пересмотра), IMP-012 (история/аудит), IMP-015 (синтетический demo). Их можно вести параллельно, если пути файлов и контракты не пересекаются. IMP-009 зависит от предметного допуска IMP-001 для live-оценки.
Этап 3 — интеграция и допуск
- IMP-016 — интеграция и e2e после появления модулей;
- IMP-019 — метрики/калибровка после IMP-014 и появления работающего OCR/оценивания;
- IMP-013 — финальный security sign-off после интеграции;
- IMP-017 — финальный деплой и smoke test;
- IMP-018 — release документация, отчёты и gate.

4. Задачи для агентов
IMP-001 — Проверить версию задания и утвердить предметный профиль
- Бизнес-цель: исключить неверный год/номер/толкование критерия до реализации оценки.
- Технический результат: проверенная запись профиля для задания ЕГЭ-2026 либо документированный STOP, если официальное задание не удаётся подтвердить; набор открытых вопросов с владельцами.
- Зависимости: нет; использовать уже существующие материалы исследования.
- Агент-исполнитель: Research Agent + предметный эксперт как утверждающий.
- Разрешённые файлы: docs/research/exam_scope.md, docs/research/criteria_analysis.md, docs/research/official_sources.md, docs/research/open_questions.md; подготовленные экспертные fixture-файлы в tests/fixtures/expert_cases/ только после согласования прав.
- Запрещённые файлы: приложение, промпты оценивания в runtime, API-контракт, схема данных, docs/product/technical_specification.md без согласования аналитика.
- Входные документы: PROJECT_CONTEXT.md; весь docs/research/; S3–S6 из реестра; руководство S4.
- Ожидаемые выходы: зафиксированные title/year/edition/page/URL; решение по критерию шкалы 0–2; вопросы/решения по пограничным случаям; правовой статус материалов; экспертное подтверждение (имя роли/дата/основание, без личных данных учеников).
- Тесты/проверка: checklist источников; сопоставление номера и текста условия с официальным комплектом одного года; проверка, что источник не считается прочитанным, если доступна только ссылка на ZIP.
- Definition of Done: точное задание и версия правил проверены; синтетические эталоны утверждены либо live scoring явно заблокирован; открытые вопросы имеют статус и владельца.
- Риски: архив недоступен, документ неокончательный, спорные правила, неясные права на публикацию.
- Проверка интегратором: ревью S1–S7 реестра и письменного решения предметного эксперта; при неполном подтверждении не снимать блокировку IMP-009.
- Размер: одно исследовательское решение/проверка источника, может разделяться на подзадачи без изменения её DoD.
IMP-002 — Утвердить ADR архитектуры, API и модель данных
- Бизнес-цель: дать независимым агентам единые контракты и избежать конфликтующих схем.
- Технический результат: принятый ADR по стеку и внешним провайдерам; API contract; data model; правила статусов и versioning; схема потоков данных и хранения.
- Зависимости: ТЗ согласовано; IMP-001 может идти параллельно, но предметный профиль остаётся условным до sign-off.
- Агент-исполнитель: System Architect.
- Разрешённые файлы: DECISIONS/ADR-001-architecture.md, API_CONTRACT.md, DATA_MODEL.md, ARCHITECTURE.md.
- Запрещённые файлы: исходники frontend/backend, docs/research/*, критерии и эталонные оценки, .env и секреты.
- Входные документы: PROJECT_CONTEXT.md, ARCHITECTURE.md, SECURITY.md, это ТЗ, requirements_traceability.md, docs/research/open_questions.md.
- Ожидаемые выходы: согласованный стек; контракты request/response; IDs; модели CriteriaProfile, Evaluation, Evidence, AuditEvent, ReviewPacket; решение о сессионном состоянии/хранилище; схема внешнего API и данных.
- Тесты/проверка: API examples валидны по выбранной схеме; статусные значения едины; нет несовместимых обязательных полей; security/privacy reviewer рассмотрел диаграмму данных.
- Definition of Done: контракты приняты frontend/backend/QA владельцами; все открытые архитектурные решения зафиксированы в ADR с последствиями.
- Риски: слишком раннее закрепление стека, неконсистентные статусы, случайное постоянное хранение ответа.
- Проверка интегратором: contract review; подтверждение, что все модули могут реализовываться без изменения общих схем.
- Размер: завершённый архитектурный контракт; не включает реализацию приложения.
IMP-003 — Подготовить UI-flow и доступный прототип
- Бизнес-цель: сделать конкурсный сценарий понятным, прозрачным и не вводящим в заблуждение.
- Технический результат: схемы экранов и состояний, включая загрузку, OCR correction, evaluation, evidence, needs_review, ошибки и demo mode.
- Зависимости: это ТЗ; API details можно уточнить после IMP-002.
- Агент-исполнитель: UX/UI Designer.
- Разрешённые файлы: docs/design/*, изображения/wireframes в docs/design/assets/*.
- Запрещённые файлы: исходники приложения, API/data model, критерии исследования и серверные настройки.
- Входные документы: technical_specification.md, user_stories.md, ACCEPTANCE_CRITERIA.md, SECURITY.md.
- Ожидаемые выходы: flow diagram; low/high fidelity screens; copy для предупреждений; states/errors; keyboard and responsive checklist.
- Тесты/проверка: пройти UC-01—UC-04 на макете; проверить визуальное разделение OCR/confirmed text, evidence/source/model interpretation и needs_review.
- Definition of Done: все основные состояния прорисованы; нет незащищённой экспертной админки; предупреждение об экспериментальной оценке заметно; дизайн доступен для реализации по контрактам.
- Риски: перегруженный экран, ложная точность, непонятная разница OCR и пользовательского текста.
- Проверка интегратором: walkthrough каждой user story и согласование фронтенд-агентом/экспертом.
- Размер: один законченный flow прототипа; не включает код UI.
IMP-004 — Создать каркас проекта и CI
- Бизнес-цель: обеспечить единый, повторяемый старт проекта для изолированных агентов.
- Технический результат: структура frontend/backend, конфигурация линтеров/форматтеров/тестов, базовый CI и безопасный .env.example.
- Зависимости: IMP-002 принят.
- Агент-исполнитель: Integrator / Platform Engineer.
- Разрешённые файлы: только согласованные в ADR конфигурационные файлы корня, .github/workflows/*, frontend/package.json/lock, backend/pyproject.toml/lock, пустые app entrypoints и тестовые health stubs.
- Запрещённые файлы: runtime критерии, оценочный промпт, UI экранные компоненты, OCR/evaluation реализация, реальные ключи/.env.
- Входные документы: ADR-001, API contract, data model.
- Ожидаемые выходы: структура проекта, инструкции dev start, CI команды, smoke health endpoint.
- Тесты/проверка: чистый clone/install/build/test; секрет-скан не находит ключи; .env.example не содержит настоящих секретов.
- Definition of Done: CI зелёный; базовый frontend/backend запускаются; версии среды фиксированы; команды описаны.
- Риски: агенты выбирают разные пакеты/пути, воспроизводимость зависимостей нарушена.
- Проверка интегратором: чистый запуск по инструкциям без локальных пользовательских настроек.
- Размер: каркас и непрерывная интеграция, без продукта.
IMP-005 — Реализовать профиль и версионирование критериев
- Бизнес-цель: гарантировать, что каждая оценка использует понятную и проверяемую версию правил.
- Технический результат: доменная схема/реестр профиля, неизменяемая версия критерия, статус verified/unverified и привязка оценки к версии.
- Зависимости: IMP-001 для подтверждения предметного профиля; IMP-002; IMP-004.
- Агент-исполнитель: Backend / Domain Agent.
- Разрешённые файлы: согласованные архитектурой файлы domain/models/schemas/repository и тесты версионирования; конфигурация только для ID профиля.
- Запрещённые файлы: frontend, OCR adapter, evaluation prompt, внешние модели, deployment config, docs/research/*.
- Входные документы: API_CONTRACT.md, DATA_MODEL.md, результат IMP-001, technical_specification.md.
- Ожидаемые выходы: CriteriaProfile/registry, метаданные источника, validation для профиля, схема сохранения criteria_version.
- Тесты: активируется только verified профиль; новая версия не меняет старую оценку; неизвестный профиль отклоняется; provenance обязателен.
- Definition of Done: unit/API contract tests проходят; profile metadata соответствует реестру источников; запрет на неподтверждённый live scoring проверен.
- Риски: случайно принять проект ЕГЭ-2027 за финальный, переиспользовать версию без решения эксперта.
- Проверка интегратором: тест «старый result + новый criteria version» продолжает ссылаться на прежнюю версию.
- Размер: один доменный модуль и его тесты.
IMP-006 — Безопасная загрузка и временная обработка файлов
- Бизнес-цель: принимать изображение без опасной обработки файлов или ненужного постоянного хранения.
- Технический результат: endpoint/service для загрузки, server-side validation, изолированное временное хранение и очистка.
- Зависимости: IMP-002, IMP-004; security review input от IMP-013.
- Агент-исполнитель: Backend / Security-aware Implementation Agent.
- Разрешённые файлы: согласованный upload route/service, upload schema, временный storage adapter, тесты upload и настройка размера/timeout из окружения.
- Запрещённые файлы: evaluation logic, критерии, frontend, логи с содержимым ответа, постоянная таблица с бинарным файлом.
- Входные документы: API contract, data model, SECURITY.md, SEC-003–SEC-004, SEC-011.
- Ожидаемые выходы: поддерживаемые image formats; фактическая проверка MIME/декодирования/размера; единые ошибки; cleanup behavior.
- Тесты: valid image; empty/corrupt/oversized/unsupported image; ложное расширение; очистка временного файла после завершения или timeout.
- Definition of Done: все негативные тесты проходят; реальные пути/имена не выдаются пользователю; содержимое файла не попадает в application log.
- Риски: parser exploit, disk exhaustion, ошибочная настройка retention.
- Проверка интегратором: автоматизированные негативные тесты и контроль cleanup на filesystem/объектном хранилище.
- Размер: один input module и security tests.
IMP-007 — Подключить OCR как сменный адаптер
- Бизнес-цель: получить черновой текст с изображения, не скрывая ошибок распознавания.
- Технический результат: OCR provider adapter с тайм-аутом/ошибками, health handling и возвратом текста плюс доступных метаданных/сигналов качества.
- Зависимости: IMP-002, IMP-006; провайдер выбирается ADR; экспертные кейсы — IMP-014.
- Агент-исполнитель: OCR / Applied AI Agent.
- Разрешённые файлы: OCR adapter/service, интерфейс провайдера, OCR unit/integration tests, benchmark script под tests/ocr/.
- Запрещённые файлы: evaluation prompt/rubric, UI компоненты, schema/API без изменения через архитектора, реальные изображения учеников.
- Входные документы: API contract, ADR по провайдеру и потокам данных, criteria_analysis.md (OCR category 10), SECURITY.md.
- Ожидаемые выходы: OCR transcript; контролируемая ошибка; конфиг timeout/provider; отчёт первичного OCR baseline.
- Тесты: читабельные synthetic image; некорректное изображение; provider timeout/error; примеры с изменённым именем/датой/термином/отрицанием.
- Definition of Done: внешние ключи только в окружении; ошибки провайдера не возвращают tracebacks; OCR output не выдаётся за подтверждённый текст; baseline указывает dataset и версию провайдера.
- Риски: внешний сервис получает исходный текст/изображение; провайдер не возвращает оценку качества; нестабильный OCR.
- Проверка интегратором: API contract test + OCR report; проверить в UI, что результат виден как draft.
- Размер: один adapter и его тестовый набор.
IMP-008 — Реализовать ручной ввод и UI корректировки OCR
- Бизнес-цель: позволить пользователю контролировать текст, который будет оценён.
- Технический результат: компонент ручного ввода, изображение/статус OCR, редактируемое поле, подтверждение final text и вызов API.
- Зависимости: IMP-002, IMP-003, IMP-004; использовать контракты загрузки IMP-006 и OCR IMP-007.
- Агент-исполнитель: Frontend Agent.
- Разрешённые файлы: согласованные frontend form/input/upload/ocr correction components и связанные UI tests.
- Запрещённые файлы: backend service, rubric/evaluation prompt, API/data contract, server logging, deployment secrets.

IMP-009 — Движок предварительного оценивания
- Бизнес-цель: превратить подтверждённый ответ в осторожную экспериментальную оценку по фиксированному критерию.

- Агент-исполнитель: Applied AI / Evaluation Agent; предметный эксперт утверждает рубрику, но не является исполнителем кода.

- Запрещённые файлы: официальный критерий без ссылки на источник, OCR, upload, UI, основной API контракт без архитектора.

- Definition of Done: не выдумывает отдельные веса; не заявляет фактическую проверку без источника; отдаёт needs_review для спорных случаев; результаты проходят тесты экспертной выборки.
- Риски: галлюцинации, переобучение на примерах, ложная уверенность, непроверяемая причина оценки.
- Проверка интегратором: golden test run и ручной review предметного эксперта; сравнить structured output со схемой API.
- Размер: один evaluator и тестовый контракт. Если модуль становится крупнее, разделить adapter и domain logic через отдельные задачи без совместной правки файлов.

6. Definition of Ready / Definition of Done
Общая Definition of Ready
Задачу разрешено брать в работу, если:
- назначен ровно один исполнитель;
- приняты зависимости;
- API/data contracts опубликованы, когда задача их использует;
- список разрешённых/запрещённых файлов однозначен;
- есть входные документы, ожидаемые выходы и способ проверки;
- все предметные утверждения ссылаются на источник, а открытые вопросы не маскируются;
- имеются синтетические фикстуры либо точный план их создания без персональных данных.
Общая Definition of Done
Задача закрывается, когда:
- реализованы только согласованные файлы;
- тесты новой функциональности проходят в CI;
- отрицательные и граничные случаи рассмотрены;
- API/data contract не нарушен или изменение согласовано архитектором и отражено в версии контракта;
- критерии/evidence/данные имеют трассировку к источникам;
- нет секретов и реальных персональных данных в diff, тестах, логах и artifacts;
- README или task report обновлён по необходимости;
- интегратор может воспроизвести результат по инструкции;
- открытые риски записаны; незакрытый блокер не считается принятым по умолчанию.
7. Релизный gate — когда допустима публичная демонстрация
Публичный конкурсный релиз разрешён, если все следующие условия подтверждены:
- [ ] Профиль, год, источник и scope явно указаны; нет ложного заявления об официальном балле.
- [ ] Импортируемые источники использованы законно; demo examples синтетические или разрешённые.
- [ ] Сквозной сценарий проходит с чистого старта.
- [ ] Ручной ввод, upload validation, OCR correction и ручной путь без OCR работают.
- [ ] Для каждого объяснения evidence относится к реальному подтверждённому тексту.
- [ ] Спорный результат может быть помечен для эксперта; передача/export прозрачен.
- [ ] В логи не попадают ответ, изображение и секреты; cleanup/retention проверены.
- [ ] Test report измеряет OCR и scoring на документированных наборах; пороги обоснованы измерением или явно помечены как не установленные.
- [ ] Security audit, dependency/container scan и секрет-скан завершены; блокирующие findings закрыты.
- [ ] README/deployment docs проверены на чистом окружении; указан rollback/лимиты/известные ограничения.
- [ ] Внешние провайдеры, лимиты и обработка данных описаны; недоступность сервиса обрабатывается честно.
